1. Database Landscape & Architectural Taxonomy

Modern cloud database engineering divides storage engines across access patterns, transaction boundaries (ACID vs. BASE), scaling paradigms (vertical scaling with read replicas vs. horizontally sharded shared-nothing partitions), and underlying storage topologies (monolithic EBS/PD vs. distributed log-structured storage fabrics).

2. Managed Relational Engines: Amazon RDS vs. Google Cloud SQL

Amazon RDS and Google Cloud SQL represent managed wrappers around traditional upstream open-source and commercial database binaries. Compute instances run on managed virtual machines attached to cloud block storage.

Amazon RDS Architecture AWS

  • Storage Underlay: Amazon EBS (gp3, io2 Block Express). Maximum storage volume size is 64 TB. Volume striping and IOPS scaling bound by EBS limits.
  • High Availability (Multi-AZ):
    • Synchronous Physical Block Replication: The primary database instance writes to an EBS volume, which synchronously replicates block deltas to a standby EBS volume in a second AZ. Failover takes 60–120 seconds (DNS CNAME switch).
    • Multi-AZ with Two Readable Standbys: Uses local NVMe transaction logging combined with commit quorums to provide sub-second transaction commit overhead and readable standby instances.
  • Read Replicas: Up to 15 read replicas per primary using asynchronous native database engine replication (e.g., MySQL binlog replication or PostgreSQL physical streaming replication). Cross-region read replicas supported.
  • Automated Backups: Daily EBS volume snapshots + continuous write-ahead log (WAL/binlog) archiving to Amazon S3, allowing Point-in-Time Recovery (PITR) down to the second.

Google Cloud SQL Architecture GCP

  • Storage Underlay: Google Cloud Persistent Disk (PD-SSD / Hyperdisk Balanced). Volumes automatically expand dynamically without database downtime (automatic storage increase up to 64 TB).
  • High Availability (HA Configuration):
    • Regional Persistent Disk Synchronous Replication: Operates at the block device level. Data written to the primary VM's disk is synchronously replicated across two zones in the same region via Regional PD.
    • Zero Engine Overhead Failover: Standby instance is maintained in a secondary zone. If the primary VM fails, the standby VM mounts the Regional PD and starts the database process (failover typically 60 seconds).
  • Read Replicas: Up to 10 cross-zone or cross-region read replicas. Replicas use native engine replication. Supports automatic cross-region replica promotion for disaster recovery.
  • Maintenance Mechanics: Supports custom maintenance windows, canary rollouts, and rolling updates with minimal downtime (sub-second switchover for MySQL/PostgreSQL HA instances).

3. Disaggregated Storage Engines: Amazon Aurora vs. Google AlloyDB

Both Amazon Aurora and Google AlloyDB redesign the traditional relational engine by separating the compute execution layer from a distributed, purpose-built storage engine designed specifically for database I/O.

================================================================================================== DISAGGREGATED STORAGE ARCHITECTURE: AURORA VS. ALLOYDB ================================================================================================== AMAZON AURORA (LOG IS THE DATABASE) GOOGLE ALLOYDB FOR POSTGRESQL [ Aurora Writer Head Node (Compute) ] [ AlloyDB Primary Instance (Compute) ] │ │ │ WAL Redo Stream Only (No Data Pages) │ WAL Stream to Storage ▼ ▼ [ Aurora Distributed Storage Fleet ] [ AlloyDB Intelligent Storage Subsystem ] ├─ 6 Storage Replicas across 3 AZs ├─ Regional Log Processing Engine (LPE) ├─ 10 GB Protection Groups ├─ Disaggregated Sharded Storage Engine ├─ 4/6 Write Quorum, 3/6 Read Quorum ├─ Auto-Tiering to Ultra-Fast NVMe Caches └─ Background Asynchronous Redo Processing └─ Dual Engine: Columnar Memory Engine (Analytical) ==================================================================================================

Amazon Aurora Internals AWS

  • "The Log is the Database": Aurora writes only WAL redo log records over the network to the storage fleet. Compute nodes never flush full dirty database pages to disk, reducing network packet traffic by up to 9x compared to traditional RDS MySQL.
  • Distributed Storage Layer:
    • Database volumes are automatically partitioned into 10 GB Protection Groups distributed across hundreds of storage nodes.
    • Every 10 GB segment is replicated 6 ways across 3 Availability Zones (2 copies per AZ).
    • Quorum Model: Write quorum requires 4 out of 6 nodes to acknowledge. Read quorum requires 3 out of 6. Tolerates loss of an entire AZ plus one additional storage node without losing write availability.
  • Read Replicas & Failover: Up to 15 Aurora Replicas share the exact same underlying storage volume. Replication lag is typically under 10–20 milliseconds. Failover takes less than 30 seconds with zero data loss ($RPO=0$).
  • Aurora Serverless v2: Scales compute capacity instantly in fine-grained increments of 0.5 Aurora Capacity Units (ACUs), adjusting CPU and RAM in-place without dropping connections.

Google AlloyDB for PostgreSQL GCP

  • Architecture & Engine: 100% PostgreSQL-compatible compute running on top of an intelligent, multi-tenant distributed storage fabric optimized for database operations.
  • Log Processing Engine (LPE):
    • Offloads heavy PostgreSQL maintenance tasks (WAL archiving, page materialization, vacuuming, and baseline backups) from the compute instances into the storage tier.
    • WAL records are continuously ingested by the storage layer and merged into base pages asynchronously.
  • AlloyDB Columnar Engine:
    • Hybrid Transactional and Analytical Processing (HTAP). Maintains an in-memory columnar representation of selected tables alongside standard row-oriented pages.
    • Automatically uses machine learning to identify analytical queries and accelerate scan/aggregation queries by up to 100x without application code modifications.
  • Fault Tolerance & High Availability: Provides a 99.99% availability SLA inclusive of maintenance. Failovers execute in less than 60 seconds. Storage scales up to 64 TB automatically with zero performance degradation.

4. Globally Distributed NewSQL: Google Cloud Spanner vs. Aurora Global / DynamoDB

Building horizontally scalable relational databases across global geographic regions requires solving distributed consensus, atomic transaction ordering, and the CAP theorem.

Google Cloud Spanner (The Standard for NewSQL) GCP

  • TrueTime API & External Consistency:
    • Spanner is the first globally distributed database to deliver External Consistency (Strict Serializability) at global scale.
    • Relies on TrueTime: a synchronized time API backed by redundant hardware reference clocks (GPS receivers and atomic Rubidium oscillators) in Google datacenters.
    • TrueTime exposes time as an uncertainty interval: $[t.earliest, t.latest]$, where $\epsilon = (t.latest - t.earliest)/2$, typically < 1 ms. Spanner introduces "commit wait" where a transaction waits out $2\epsilon$ before releasing locks, guaranteeing monotonically increasing commit timestamps globally without inter-region lock coordination.
  • Consensus & Storage Topology:
    • Data is sharded horizontally into Splits. Each Split is replicated across zones/regions using a Paxos consensus group.
    • Writes require a Paxos majority quorum. Distributed transactions spanning multiple splits use a Two-Phase Commit (2PC) protocol running over the Paxos groups.
  • Availability & Multi-Region SLA: Multi-region instances offer an industry-leading 99.999% (five 9s) availability SLA with zero planned downtime and zero data loss ($RPO=0, RTO=0$).

AWS Multi-Region Topologies: Aurora Global & DynamoDB AWS

  • Amazon Aurora Global Database:
    • Single-Writer, Multi-Reader: Dedicated writer in one primary region; up to 5 secondary read-only regions.
    • Storage-Layer Asynchronous Replication: Dedicated storage nodes replicate WAL records directly across regions over the AWS private backbone. Cross-region replication latency is typically under 1 second.
    • Consistency Boundary: Eventual consistency for cross-region reads. If the primary region fails, a secondary region can be promoted with an RPO < 1 second and RTO < 1 minute. Cannot perform active-active distributed multi-region ACID writes.
  • DynamoDB Global Tables:
    • Multi-Master Distributed NoSQL: Active-active multi-region database. Any region can accept concurrent read and write operations.
    • Conflict Resolution: Operates under Last-Writer-Wins (LWW) based on client-side or system NTP timestamps. Lacks multi-row multi-region ACID transactional consensus across regions.

5. Key-Value & Document NoSQL: Amazon DynamoDB vs. Google Cloud Firestore

Massive scale web and mobile applications require predictable single-digit millisecond latency, automated horizontal sharding, and flexible semi-structured JSON storage.

Amazon DynamoDB Architecture AWS

  • Data Model: Key-Value and Document store. Each item requires a Partition Key (PK) (determines physical hash partition) and an optional Sort Key (SK) (determines sorted order within the partition).
  • Partitioning & Throughput:
    • Hash function maps the PK to a 128-bit integer space distributed across internal storage nodes.
    • A single partition accommodates up to 10 GB of data, 1,000 Write Capacity Units (WCUs), and 3,000 Read Capacity Units (RCUs). Partitions split automatically as storage or traffic expands.
    • Adaptive Capacity automatically allocates bursts to hot partitions.
  • Transactions & Consistency:
    • Reads: Eventually Consistent (default, 0.5 RCU per 4 KB) or Strongly Consistent (1 RCU per 4 KB).
    • TransactWriteItems / TransactGetItems: ACID transactions across up to 100 items or 4 MB of data within an AWS account and region, using a two-phase commit protocol.
  • Change Data Capture (CDC): DynamoDB Streams (24-hour strictly ordered shard-level commit log) and Kinesis Data Streams integration.

Google Cloud Firestore Architecture GCP

  • Data Model: Hierarchical document database. Documents reside inside Collections. Documents contain key-value fields and can host nested subcollections, forming natural tree hierarchies.
  • Dual Operating Modes:
    • Firestore Native Mode: Real-time WebSocket subscriptions, client SDK offline caching, automated multi-region replication, and mobile/web direct access protected by Security Rules.
    • Datastore Mode: High-throughput backend server workloads, removing client-SDK features in favor of higher write throughput (millions of writes/sec) and lower latency.
  • Indexing & Query Engine:
    • Automatically indexes every field in a document. Supports single-field, composite, and collection-group indexes.
    • Queries are shallow (retrieving documents without fetching subcollections) and scale proportionally to the size of the result set, not the total size of the dataset.
  • Transactions: True ACID distributed multi-document transactions using optimistic concurrency control (OCC).

6. Wide-Column & Analytical NoSQL: Google Cloud Bigtable vs. Amazon Keyspaces

Petabyte-scale operational applications—such as financial trading telemetry, IoT metrics, and real-time fraud detection—demand consistent sub-10ms writes and high-density sequential scans.

Google Cloud Bigtable (The Original Wide-Column Engine) GCP

  • Storage Architecture (SSTables & Tablets):
    • Bigtable decouples compute from storage entirely. Compute runs on Bigtable Nodes; storage is persisted in Google's distributed file system (Colossus) as immutable SSTables (Sorted String Tables).
    • Tables are split horizontally into ranges of contiguous rows called Tablets. Tablets are balanced dynamically across Bigtable worker nodes.
    • Rebalancing or adding nodes involves simple metadata pointer updates; no physical data movement occurs between nodes, enabling instantaneous scaling.
  • Access Patterns: Single row-key lookups, prefix scans, and range scans. Row keys are sorted lexicographically. Writes are atomic at the single-row level.
  • Ecosystem Compatibility: Native API matches Apache HBase; integrates with Apache Spark, Dataflow, and BigQuery (federated queries).

Amazon Keyspaces (for Apache Cassandra) AWS

  • Serverless Cassandra Engine: Fully managed, serverless Apache Cassandra 3.11/4.x compatible database. Translates Cassandra Query Language (CQL) calls onto an internal AWS storage subsystem.
  • Decoupled Architecture: Replaces Cassandra's traditional ring topology, gossip protocol, and manual node repair operations with a cloud-native serverless architecture.
  • Capacity Modes: Supports On-Demand capacity (pay-per-request) and Provisioned capacity with application auto-scaling.
  • High Availability: Tables are automatically replicated 3 ways across separate Availability Zones within the region.

8. Specialized Engines: Graph, Document, Time-Series & Vector

AWS Specialized Database Portfolio AWS

  • Amazon Neptune: Purpose-built, high-performance graph database. Supports Property Graph (Apache TinkerPop Gremlin, openCypher) and W3C RDF (SPARQL). Built on the Aurora disaggregated 6-way replicated storage fabric.
  • Amazon DocumentDB: Fully managed MongoDB 4.0/5.0 API-compatible document database. Built on Aurora's decoupled storage engine, converting MongoDB BSON documents into internal block formats.
  • Amazon Timestream: Serverless time-series database for IoT and operational monitoring. Features automated storage tiering (in-memory store for recent data; cost-effective magnetic store for historical data).
  • Vector Capabilities: Native vector search supported in Amazon Aurora PostgreSQL (via pgvector), OpenSearch Service, and Neptune Analytics.

Google Cloud Specialized & Multi-Model Portfolio GCP

  • Cloud Spanner Graph: Combines full ACID relational capabilities with native property graph queries using the standard ISO GQL (Graph Query Language). Eliminates the need to synchronize data between separate relational and graph engines.
  • Firestore Vector Search: Natively indexes document embeddings via Hierarchical Navigable Small World (HNSW) and Flat vector indexes for generative AI retrieval.
  • AlloyDB AI: Integrated vector engine enabling embedding generation and similarity search within PostgreSQL, accelerating vector lookups up to 10x compared to standard pgvector.
  • Vertex AI Vector Search (formerly Matching Engine): Enterprise-grade, low-latency approximate nearest neighbor (ANN) vector database scaling to billions of vectors.

9. Storage Internals, Quorums & Replication Mechanics

Staff-level engineers must understand the mathematical and physical mechanisms governing transaction commits across distributed hardware.

System Consensus Protocol Quorum Formulation Failover Mechanics & RPO / RTO
Amazon Aurora Asynchronous Gossip + Log Quorum $V=6, W=4, R=3$ across 3 Availability Zones. Tolerates $2$ node failures without write loss; $3$ node failures without read loss. Standby replica promoted via shared storage pointer update. $RPO = 0$, $RTO < 30\text{s}$.
Google Cloud Spanner Multi-Paxos + Two-Phase Commit (2PC) Paxos majority quorum: $Q = \lfloor n/2 \rfloor + 1$ per split. Multi-region requires majorities across multiple geographic locations. Leader election handled automatically within Paxos group. $RPO = 0$, $RTO = 0$ (transparent continuous availability).
Amazon DynamoDB Paxos / Raft variant per partition 3-way synchronous replication across 3 AZs. Write quorum acknowledged once 2 of 3 replicas commit to local transaction log. Automatic leader election per partition. Unhealthy storage nodes replaced dynamically. $RPO = 0$, $RTO < 1\text{s}$.
Google Cloud Bigtable Shared-storage tablet pointers (Colossus) Storage layer handles block-level replication (Colossus Reed-Solomon encoding). Bigtable compute nodes coordinate via Google Chubby (Paxos lock service). Tablet reassignment to healthy node via Chubby lock release. $RPO = 0$, $RTO < 10\text{s}$.

11. Principal-Level System Design & Interview Scenarios

Scenario A: Global Core Banking Ledger with Active-Active Cross-Continental Consistency

Design Challenge: Architect a financial ledger requiring active writes across US, Europe, and Asia. Strict serializability is mandatory to prevent double-spending. Down time tolerance is zero ($RTO = 0, RPO = 0$).

  • AWS Evaluation:
    • Aurora Global Database: Secondary regions are read-only. Writes must traverse to the primary writer region, incurring cross-continental network latency and presenting a single point of failure for write availability.
    • DynamoDB Global Tables: Multi-master writes are permitted, but conflict resolution is Last-Writer-Wins (LWW). Lacks multi-row distributed ACID isolation required for balance transfers.
  • GCP Solution (Optimal Architecture):
    • Deploy Google Cloud Spanner with a Multi-Region Instance Configuration (e.g., nam-eur-asia1).
    • Spanner uses TrueTime and Paxos groups across continents to guarantee external consistency (strict serializability).
    • Balance transfers execute as ACID distributed transactions using Two-Phase Commit over Paxos. Even if an entire continent's cloud region experiences a blackout, the remaining witness and read-write replicas maintain Paxos quorum with zero data loss ($RPO = 0$) and uninterrupted write availability (99.999% SLA).
Scenario B: High-Throughput E-Commerce Flash Sale Architecture

Design Challenge: A retail platform experiences flash sales spiking from 5,000 requests/sec to 1,500,000 requests/sec in under 30 seconds. Data consists of item inventory, user shopping carts, and order processing.

  • AWS Architecture:
    • Session State & Caching: Amazon ElastiCache Serverless (Redis/Valkey) instantly scales memory and compute to absorb traffic spikes without manual shard provisioning.
    • Shopping Cart & Inventory: Amazon DynamoDB configured in On-Demand Capacity Mode. Partition keys use synthetic sharding (e.g., item_id + "_" + random(1, 20)) to prevent hot-partition throttling.
    • Order Processing: Orders are emitted via DynamoDB Streams to AWS Lambda, buffered into SQS FIFO queues, and committed asynchronously to an Amazon Aurora Serverless v2 cluster.
  • GCP Architecture:
    • Session & Caching: Cloud Memorystore for Redis Cluster with auto-scaling to absorb peak read load.
    • User Carts & Catalog: Cloud Firestore (Datastore Mode), automatically scaling horizontal document writes across Google's distributed Megastore/Spanner substrate.
    • Analytics & Fraud Detection: Parallel stream writes directed into Cloud Bigtable, delivering sub-5ms write latencies at millions of writes per second for real-time fraud scoring models.
