1. SDN Fabrics & Core Network Underlay

Before analyzing user-facing VPC features, an architect must understand the physical and software-defined underlay powering both cloud providers. Network behavior during micro-bursts, MTU sizing, and jitter stems directly from these substrate architectures.

AWS Nitro & ENA Architecture AWS

AWS implements software-defined networking at the hypervisor edge via proprietary hardware: AWS Nitro System.

  • Elastic Network Adapter (ENA): Dedicated ASIC/FPGA PCI device offloading network processing (encapsulation, security group checks, metering) from the host CPU.
  • Underlay Fabric: Clos-topology non-blocking datacenter fabric built on custom switches and SRD (Scalable Reliable Datagram) protocol for high-performance HPC/EFA workloads.
  • Encapsulation: Proprietary Geneve-like overlay wrapping customer L2 frames into VPC L3 packets.
  • MTU Mechanics: Supports 1500 bytes standard; 9001 bytes (Jumbo frames) within a single VPC or peered VPCs within the same region. Across Transit Gateways, Direct Connect, and Inter-Region Peering, MTU caps at 8500 or 1500 bytes.

Google Andromeda & Jupiter Fabric GCP

Google Cloud operates a unified global network running on its custom-built multi-tier Jupiter Fabric.

  • Andromeda SDN: A distributed software-packet-processing substrate. Control plane coordinates Hoverboards (packet-processing nodes) and local On-Host vSwitch instances running in software and hardware acceleration (IPUs).
  • Global Fiber Backbone (B4 / B2): Google operates the world's largest private backbone. Inter-region and edge-to-region traffic travels entirely over private fiber rather than the public transit internet.
  • Encapsulation: Custom encapsulation protocol over Andromeda tunnels running directly on Google's Jupiter Clos network.
  • MTU Mechanics: Default 1460 bytes (due to overlay overhead). Supports 1500 bytes standard and 8896 bytes (Jumbo frames) configurable at VPC creation.

2. VPC Topologies, Subnets & Routing Engines

The primary architectural bifurcation between AWS and GCP lies in the scope and nature of the Virtual Private Cloud (VPC).

AWS Regional VPC Architecture AWS

  • Scope: Strictly Regional. A VPC spans all Availability Zones (AZs) in a single AWS Region. To connect workloads across regions, inter-region peering or transit networks are mandatory.
  • Subnets: Strictly Zonal. A subnet must reside entirely within a single AZ and maps to a specific CIDR block. High-availability requires creating at least 2 or 3 subnets across separate AZs.
  • Routing Engine: Explicit Route Tables. Each subnet is explicitly associated with a Route Table. Local route (VPC CIDR) cannot be modified or deleted. Routing operates via longest prefix match (LPM).
  • IP Addressing: Primary IPv4 CIDR block (RFC 1918) between /16 and /28. Up to 4 secondary IPv4 CIDR blocks can be appended. Supports dual-stack IPv6 (/56 assigned per VPC, /64 per subnet).
  • Reserved Addresses: First 4 and last 1 IP address in every subnet CIDR are reserved by AWS (e.g., in 10.0.0.0/24: .0 network, .1 router, .2 DNS, .3 future, .255 broadcast).

GCP Global VPC Architecture GCP

  • Scope: Natively Global. A single GCP VPC spans every Google Cloud region across the globe without requiring inter-region peering or transit gateways.
  • Subnets: Regional. Subnets span all Availability Zones within their designated region. Instances across multiple zones in the same region reside in the exact same subnet and broadcast domain abstraction.
  • Routing Engine: Distributed Global Routing Engine. Routes are global objects. Subnet routes are generated automatically. Dynamic routing can be configured in Regional (default) or Global dynamic routing mode.
  • IP Addressing: Primary IPv4 CIDR per subnet. Supports Alias IP ranges (attaching secondary CIDRs to specific VM interfaces, vital for Kubernetes Pod CIDRs). Dual-stack IPv6 (internal /64 or external /64).
  • Reserved Addresses: First 2 and last 2 IP addresses reserved by Google (e.g., in 10.0.0.0/24: .0 network, .1 default gateway, .254 reserved by GCP, .255 broadcast).

3. Internet Edge, Gateways & NAT Architecture

Handling ingress and egress between private resources and the public internet requires resilient gateway constructs that scale dynamically without dropping flows.

AWS Internet Gateway & NAT Gateway AWS

  • Internet Gateway (IGW): Horizontally scalable, redundant, VPC-level software gateway. Performs 1:1 stateful NAT translation between private IP addresses and public IPv4/IPv6 Elastic IPs. Zero bandwidth bottleneck (scales to multiple Terabits).
  • Egress-Only Internet Gateway: IPv6-only egress construct preventing unsolicited inbound connections.
  • NAT Gateway: Managed regional/zonal service providing outbound IPv4 connectivity for private subnets.
    • Zonal Scope: Deployed inside a specific AZ. To ensure high availability, an architect must deploy one NAT Gateway per AZ and route each private AZ subnet to its respective local NAT GW.
    • Bandwidth & Limits: Scales from 5 Gbps up to 100 Gbps per NAT GW automatically. Allocates up to 55,000 concurrent connections per Elastic IP to a single destination.
    • Cost Impact: Incurs hourly instance fee + per-GB data processing fee + inter-AZ data transfer fees if crossed.

GCP Cloud NAT & Default Internet Gateway GCP

  • Default Internet Gateway: Built-in next-hop route (0.0.0.0/0 -> default-internet-gateway) handling traffic for VMs with external IP addresses. Operates at the Andromeda SDN level with no physical appliance or bottleneck.
  • Cloud NAT: Fully distributed, software-defined managed NAT service implemented in Andromeda.
    • Regional/Global Scope: Cloud NAT is configured on a Cloud Router. It is regional and automatically applies to all VMs across all zones within that region without deploying individual instances or gateways.
    • No Single Point of Failure: Since it is programmed into the on-host Andromeda switch, there is no physical NAT appliance, middle-box hop, or choke point.
    • Port Allocation: Supports Dynamic Port Allocation (allocates ports to VMs based on demand) or static port reservation per VM (default: 64 ports per VM, expandable up to 65,536).
    • Private NAT: Supports Inter-VPC NAT translation for overlapping RFC 1918 CIDRs across hybrid networks.

4. Multi-VPC, Hub-and-Spoke & Mesh Interconnects

As organizations expand beyond dozens of VPCs, peer-to-peer full-mesh configurations become unmanageable ($O(n^2)$ complexity). Both clouds offer scalable hub-and-spoke solutions.

AWS VPC Peering & Transit Gateway (TGW) AWS

  • VPC Peering: Point-to-point connection between two VPCs. Non-transitive (A-B and B-C does not allow A-C). No single point of failure; traffic stays on the AWS private backbone. Supports cross-region and cross-account.
  • AWS Transit Gateway (TGW): Regional high-performance network transit hub.
    • Acts as a cloud router. Uses Elastic Network Interfaces (ENIs) attached to subnets in each AZ.
    • Supports multiple isolated route tables for network segmentation (e.g., Prod, Non-Prod, Shared Services, Inspection VPC).
    • Maximum throughput: Up to 50 Gbps per VPC attachment burst; multi-TGW scales linearly.
    • Supports multicast routing and inter-region peering between TGWs.
  • AWS Cloud WAN: Centralized WAN orchestrator that provisions and manages global core networks across multiple AWS Regions and on-premises environments via declarative policy documents.

GCP VPC Peering & Network Connectivity Center GCP

  • VPC Network Peering: Connects two VPCs globally. Like AWS, it is non-transitive. However, because GCP VPCs are global, peering allows instant worldwide low-latency communication across regions.
    • Custom routes (static/dynamic) can be imported/exported across the peering boundary.
    • Internal DNS names are resolvable across peered VPCs.
  • Shared VPC: A fundamental GCP differentiator. A Host Project shares its subnets with multiple Service Projects. Service projects deploy compute/container resources directly into centrally managed subnets governed by network engineers.
  • Network Connectivity Center (NCC): A global management hub connecting hybrid networks (Site-to-Site VPN, Cloud Interconnect, Third-Party SD-WAN routers) and VPCs directly into Google's global backbone using standard BGP peering.

Architectural Insight: The Google Cloud Router Advantage

In GCP, all dynamic routing across VPNs and Interconnects is terminated on a Cloud Router. A Cloud Router does not sit in the data path (it does not process packets); it only handles the BGP control plane. Once routes are learned via BGP, the Cloud Router directly programs Andromeda's distributed virtual switch fabric. If a Cloud Router goes down or experiences control-plane flap, the data-plane continues forwarding packets uninterrupted.

6. Private Service Endpoints & Zero-Trust Access

Consuming SaaS applications or cloud PaaS services (such as object storage or managed databases) without traversing the public internet is essential for regulatory compliance (PCI-DSS, HIPAA, FedRAMP).

AWS PrivateLink & VPC Endpoints AWS

  • Gateway Endpoints: Legacy routing-table entry for Amazon S3 and DynamoDB only. Injects a route into the VPC route table pointing to an AWS gateway prefix list. Free of charge, does not support transit VPCs or cross-region access directly.
  • Interface Endpoints (PrivateLink): Allocates an Elastic Network Interface (ENI) with a private IP from your subnet.
    • Powered by AWS Hyperplane (internal distributed network proxy).
    • Supports almost all AWS PaaS APIs, customer-hosted services behind NLBs, and third-party SaaS (Snowflake, Databricks).
    • Binds to Private DNS names for transparent failover.
    • Controlled via Security Groups and Endpoint Policies (IAM policies attached to the endpoint).

GCP Private Service Connect & Access Patterns GCP

  • Private Google Access (PGA): Subnet-level toggle enabling VMs without external IPs to reach Google APIs (Storage, BigQuery) via private internal IPs routed to private.googleapis.com (199.36.153.8/30) or restricted.googleapis.com (199.36.153.4/30).
  • Private Services Access (PSA): Peering connection between customer VPC and a Google-managed VPC (used for Cloud SQL, Memorystore). Requires reserving an RFC 1918 CIDR block.
  • Private Service Connect (PSC): The next-generation zero-trust endpoint framework.
    • PSC Endpoints: Allocates an internal IP address directly inside your VPC that targets Google APIs, producer services, or third-party SaaS.
    • Avoids IP address conflicts entirely (no shared RFC 1918 peering requirements).
    • Producer publishes a service behind an Internal Load Balancer; consumer maps a single IP to that service attachment via Service Directory.

7. Load Balancing Architectures & Traffic Flow

Cloud load balancers dictate application latency, TLS termination capabilities, packet preservation, and cross-region failover.

AWS Elastic Load Balancing (ELB) Family AWS

  • Application Load Balancer (ALB - Layer 7): Advanced HTTP/HTTPS, gRPC, and WebSocket reverse proxy. Supports path-based, host-based, query-param, and HTTP-header routing. Terminate TLS, integrates with AWS WAF and Cognito. Operates as proxy instances scaled across AZs.
  • Network Load Balancer (NLB - Layer 4): Ultra-high-performance TCP/UDP/TLS load balancer.
    • Powered by Hyperplane. Handles millions of requests per second with microsecond latency.
    • Preserves client source IP address natively without proxy protocol.
    • Provides a static IP address per AZ (supports Elastic IPs).
  • Gateway Load Balancer (GWLB - Layer 3/4): Simplifies deployment of third-party virtual appliances (Palo Alto, Fortinet, Check Point). Uses Geneve encapsulation to preserve packet metadata across appliance boundaries.
  • Global Distribution: AWS ALBs and NLBs are regional. Global routing requires AWS Global Accelerator (Anycast IP routing traffic over AWS private fiber to regional NLBs/ALBs) or Route 53 Latency/Failover DNS.

GCP Cloud Load Balancing (GCLB) Portfolio GCP

  • Global External Application Load Balancer: Fully distributed software-defined Layer 7 reverse proxy implemented on Google's global Edge Front End (GFE) servers.
    • Single Global Anycast IP: One IPv4 and IPv6 VIP handles traffic worldwide. Client enters Google's private backbone at the closest PoP (Cold Potato routing).
    • Zero warm-up required: Handles massive traffic spikes instantly without pre-warming.
    • Automatic cross-region failover: If a region fails, traffic instantly shifts to healthy backends in another continent.
  • Regional External / Internal Application Load Balancer: Envoy-based proxy load balancer for workloads requiring strict regional compliance or private internal microservices.
  • Internal Passthrough Network Load Balancer (Layer 4): Software-defined direct server return (DSR) load balancer.
    • Zero latency overhead: Packets are delivered directly to VMs via Maglev SDN routing without intermediate proxy hops.
    • Preserves client IP, port, and protocol natively.

8. Network Firewalls & Perimeter Defense

A defense-in-depth model combines stateful Layer 4 filtering at the network interface with deep Layer 7 stateful inspection engines.

AWS Security Groups, NACLs & Network Firewall AWS

  • Security Groups (Layer 4): Stateful virtual firewalls attached to ENIs.
    • Allow-only rules (cannot write an explicit deny). Return traffic is automatically permitted regardless of inbound rules.
    • Can reference other Security Groups as sources (dynamic membership based on instance tags).
  • Network Access Control Lists (NACLs - Layer 4): Stateless subnet-level boundaries.
    • Evaluated sequentially by rule number. Explicit allow and deny rules.
    • Requires opening ephemeral return ports (1024-65535) manually.
  • AWS Network Firewall: Managed stateful inspection service powered by the open-source Suricata engine.
    • Deploys into inspection subnets with dedicated endpoints.
    • Provides 5-tuple filtering, Snort/Suricata IPS rule sets, and domain list filtering (TLS SNI inspection).
  • AWS WAF & Shield: Layer 7 Web Application Firewall protecting ALBs, CloudFront, and API Gateways against SQLi, XSS, and rate-limiting. Shield Standard (free L3/L4 DDoS) and Shield Advanced (DDoS response team and financial protection).

GCP Firewall Policies, Cloud Armor & Cloud IDS GCP

  • VPC Firewall Rules (Layer 4): Stateful firewalls applied at the VPC level.
    • Supports both Allow and Deny rules with explicit priority numbers (0 to 65535).
    • Applied via Network Tags or Service Accounts (identity-based firewalling).
  • Hierarchical Firewall Policies: Enforced at Organization or Folder levels.
    • Evaluated before any VPC-level rules. Security teams mandate immutable perimeter rules (e.g., block SSH/RDP from public internet globally) that project owners cannot override.
  • Cloud Armor: Enterprise enterprise-grade DDoS mitigation and WAF built on Google's global infrastructure.
    • Inspects traffic at the Edge PoP before reaching the VPC.
    • Supports Layer 7 filtering, OWASP Top 10 rules, ML-based adaptive rate-limiting, and reCAPTCHA Enterprise bot detection.
  • Cloud IDS: Managed intrusion detection system powered by Palo Alto Networks threat engine, inspecting mirrored traffic for malware, exploits, and command-and-control activity.

10. Observability, Packet Mirroring & Telemetry

Troubleshooting intermittent connectivity issues, auditing network access, and verifying compliance requires packet-level flow telemetry and deterministic path analysis.

AWS Network Observability Stack AWS

  • VPC Flow Logs: Captures 5-tuple metadata (src/dst IP, port, protocol, packets, bytes, action: ACCEPT/REJECT). Exportable to Amazon CloudWatch Logs, S3, or Kinesis Data Firehose. Configurable at VPC, Subnet, or ENI level. Aggregation intervals: 1 min or 10 min.
  • Traffic Mirroring: Out-of-band capture of native raw L2 payload from an ENI. Encapsulates full packets into VXLAN (port 4789) and sends them to a monitoring target (NLB or EC2 instance running Zeek/Wireshark).
  • VPC Reachability Analyzer: Static configuration analysis tool. Uses formal logic to determine whether an ENI can communicate with another ENI, IGW, or Peering connection without sending test packets.
  • Network Access Analyzer: Automated reasoning engine verifying whether network access paths satisfy security boundaries (e.g., verifying database subnets have zero inbound paths from an IGW).

GCP Network Intelligence Center GCP

  • VPC Flow Logs: Sampled metadata captured in Andromeda without performance penalty. Real-time streaming into Cloud Logging and BigQuery. Configurable sample rate (from 0.0001% up to 100%) and aggregation window (5s, 30s, 1m, 5m). Includes RTT (Round Trip Time) metrics.
  • Packet Mirroring: Clones full ingress/egress packet payloads from Compute Engine VMs and delivers them to an Internal Passthrough NLB forwarding to an array of security collectors.
  • Connectivity Tests: Proactive diagnostic tool. Simulates packet paths between source and destination using live configuration analysis (routes, firewalls, hierarchical policies, VPC-SC). Validates whether traffic is dropped or permitted and points out the exact blocking rule.
  • Performance Dashboard: Displays real-time packet loss and latency across all GCP regions, zones, and paths to specific on-premises locations over Interconnect.
