2. Cryptography, Key Management & Hardware Security

Envelope encryption is the foundational pattern for both AWS and GCP. Data is encrypted locally with a Data Encryption Key (DEK), and the DEK is encrypted under a Key Encryption Key (KEK) maintained inside a Hardware Security Module (HSM).

AWS Key Management Service (KMS) & CloudHSM AWS

  • Key Architecture:
    • AWS Owned Keys: Managed entirely by AWS; customer has no visibility or CloudTrail audit logging.
    • AWS Managed Keys: Created automatically on behalf of a service (e.g., aws/s3). Rotates every year automatically. Cannot modify policy.
    • Customer Managed Keys (CMKs): Full policy control, rotation options (annual or on-demand), and CloudTrail visibility.
    • Multi-Region Keys (MRKs): Primary key in one region replicated to secondary regions with identical key material and Key ID. Enables decrypting cross-region ciphertexts locally without cross-region network calls.
  • Cryptographic Underlay: Proprietary hardware HSMs validated at FIPS 140-2 Level 3 (overall Level 2).
  • AWS CloudHSM: Single-tenant, dedicated FIPS 140-2 Level 3 HSM appliances provisioned directly into customer VPCs. Customer manages PKCS#11, JCE, and OpenSSL cryptographic users directly. AWS has zero access to key material.
  • Custom Key Stores: Backs AWS KMS with dedicated AWS CloudHSM clusters or an on-premises external key manager (XKS).

GCP Cloud KMS, Cloud HSM & Cloud EKM GCP

  • Key Hierarchy: KeyRing (regional/global container) $ ightarrow$ CryptoKey $ ightarrow$ CryptoKeyVersion.
  • Protection Levels:
    • SOFTWARE: Software-backed keys protected by Google's internal cryptographic root of trust.
    • HSM: Backed by FIPS 140-2 Level 3 hardware security modules. Managed transparently without cluster maintenance overhead.
    • EXTERNAL (Cloud EKM): Coordinates with external on-premises HSMs (Thales, Fortanix, Entrust). Keys never enter Google Cloud. Every cryptographic operation issues a gRPC call over a VPC or private interconnect to the customer's on-premises HSM.
    • EKM with Key Access Justifications (KAJ): Transmits a programmatic justification with every decrypt request. The customer's external HSM automatically blocks decryption if Google's automated operational justification is unauthorized (e.g., preventing administrative subpoena access).
  • Autokey: Automates KMS key creation and IAM binding provisioning according to resource security guidelines during Terraform deployment.

3. Secrets Management & Public Key Infrastructure (PKI)

Hardcoded credentials and unmanaged TLS certificates represent primary attack vectors. Modern architectures automate certificate issuance and credential rotation.

Capability Amazon Web Services (AWS) Google Cloud Platform (GCP)
Secrets Storage & Lifecycle AWS Secrets Manager: Encrypted with KMS CMKs. Versioning uses staging labels (AWSCURRENT, AWSPREVIOUS, AWSPENDING). Max secret size: 64 KB. Secret Manager: Global or regional secret replication. Managed versioning (integers: 1, 2, latest). Max payload size: 64 KiB. Automatic destroyed-state delayed wiping.
Automated Credential Rotation Native Lambda integration out-of-the-box for RDS (PostgreSQL, MySQL), DocumentDB, and Redshift. Multi-step rotation lifecycle preventing lockouts. Event-driven via Cloud Pub/Sub and Cloud Run / Cloud Functions. Rotation triggers scheduled via Cloud Scheduler.
Private CA Management AWS Private CA: Fully managed private certificate authority. Root and subordinate CAs. Issues X.509 certificates with CRLs and OCSP validation. Audited to FIPS 140-2 Level 3 HSMs. Certificate Authority Service (CAS): Scalable managed CA. Tiered into DevOps (high-volume, short-lived container certs) and Enterprise tiers. Highly configurable certificate profiles.
Public TLS Management AWS Certificate Manager (ACM): Free public SSL/TLS certificates with automatic DNS validation and auto-renewal for ALBs, CloudFront, and API Gateways. Certificate Manager: Google-managed SSL/TLS certificates supporting single domain, multi-domain (SAN), and wildcard certificates for Cloud Load Balancing.

4. Data Loss Prevention & Sensitive Data Discovery

Automated discovery, classification, and remediation of PII, financial information (PCI), and health records (HIPAA) residing across object storage and analytical datasets.

Amazon Macie AWS

  • Scope: Dedicated sensitive data discovery service designed specifically for Amazon S3.
  • Operational Engine:
    • Automated Sensitive Data Discovery: Continuously evaluates S3 buckets across an organization using intelligent sampling techniques to identify sensitive data footprints without scanning every byte.
    • Uses machine learning and pattern-matching classifiers to detect PII (national IDs, credit cards, credentials).
    • Generates deep security posture findings: flags publicly accessible buckets, unencrypted buckets, or buckets shared outside the AWS Organization.
  • Limitations: Limited to S3. Does not natively scan block storage, databases, or incoming API streams.

Sensitive Data Protection (Cloud DLP) GCP

  • Scope: Comprehensive discovery, classification, and real-time de-identification platform spanning Cloud Storage, BigQuery, Datastore, and custom application pipelines.
  • Operational Engine:
    • Over 150 built-in infoTypes with custom regex, dictionary, and context-rule support.
    • Continuous discovery profiling across all BigQuery tables and Cloud Storage buckets at project or organizational scale.
    • Data Transformation & Tokenization Engine: Performs format-preserving encryption (FPE), cryptographic hashing, bucketing, masking, and differential privacy transformations directly on data streams before storing.
  • Advantage: Can be invoked synchronously via API in streaming architectures (e.g., sanitizing logs in Cloud Run before writing to BigQuery).

Analyzing control-plane activity, data-plane events, and OS runtime behavior to identify malicious actors and zero-day compromises.

Amazon GuardDuty Internals AWS

  • Agentless Ingestion: Ingests AWS CloudTrail, VPC Flow Logs, and Route 53 DNS logs directly from the AWS hypervisor and network fabric without requiring customer log exports or impacting workload throughput.
  • Extended Detection Engines:
    • EKS Protection: Evaluates Kubernetes API audit logs and deploys an optional eBPF runtime security agent to detect process and network anomalies inside pods.
    • RDS Protection: Profiles Aurora database access patterns to detect anomalous logins and brute-force attempts.
    • Lambda Protection: Monitors serverless invocation telemetry for cryptomining and unauthorized outbound calls.
    • Malware Protection: Automatically creates an EBS snapshot and performs agentless malware scanning when suspicious activity is flagged on an EC2 instance.

Google Cloud SCC Threat Detection Portfolio GCP

  • Event Threat Detection (ETD): Analyzes organization-wide Cloud Logging streams in real time. Detects brute-force SSH, IAM privilege escalation, cryptomining, malware C2 communication, and anomalous data exfiltration.
  • Virtual Machine Threat Detection (VMTD):
    • Hypervisor-Level Agentless Memory Scanning: Operates at Google's hypervisor layer. Inspects the active volatile memory of running Compute Engine VMs without installing in-guest agents or stealing CPU cycles.
    • Detects kernel-level rootkits, running cryptominers, and memory-only malware invisibly to the compromised guest OS.
  • Container Threat Detection (CTD): Traces kernel syscalls inside GKE worker nodes to detect reverse shells, unauthorized binaries, and compromised container escapes.

7. Posture Management & Workload Protection (CSPM & CWPP)

AWS Security Hub & Amazon Inspector AWS

  • AWS Security Hub (CSPM):
    • Central aggregation pane for findings from GuardDuty, Inspector, Macie, IAM Access Analyzer, and AWS Config.
    • Runs automated continuous compliance checks mapped against industry benchmarks: CIS AWS Foundations Benchmark, PCI-DSS, and NIST SP 800-53.
    • Calculates automated security posture scores across accounts.
  • Amazon Inspector (CWPP):
    • Continuous, automated vulnerability management for Amazon EC2 instances, AWS Lambda functions, and container images stored in Amazon ECR.
    • Agentless scanning for EC2 (via EBS snapshot analysis) or agent-based via AWS Systems Manager (SSM).
    • Evaluates CVEs, generates Common Vulnerability Scoring System (CVSS) scores contextualized with network reachability analysis.

Google Cloud Security Command Center (SCC) GCP

  • SCC Posture Management (CSPM):
    • Central security console for the entire Google Cloud Organization.
    • Continuously monitors assets via Cloud Asset Inventory. Evaluates misconfigurations against CIS GCP Foundations, PCI-DSS, ISO 27001, and SOC 2.
    • Attack Path Simulation: Maps potential lateral movement paths by combining IAM permissions, resource exposure, and network reachability to identify high-value asset risks.
  • SCC Workload Protection (CWPP):
    • Scans Compute Engine VMs for OS vulnerabilities and package risks.
    • Container vulnerability scanning integrated into Artifact Registry and Google Kubernetes Engine (GKE) runtime posture dashboards.
    • Web Security Scanner: Crawls public App Engine, Compute Engine, and GKE web apps to identify XSS, Flash injection, and cleartext passwords.

9. Hardware-Enforced Isolation & Confidential Computing

Confidential computing protects data in-use (in memory) by cryptographically isolating workloads from the hypervisor, system operators, and cloud provider administrators.

AWS Nitro Enclaves & Confidential EC2 AWS

  • AWS Nitro Enclaves:
    • Creates isolated, hardened execution environments alongside an EC2 instance.
    • An enclave has no persistent storage, no external network interface, and no interactive access (no SSH, no admin credentials).
    • Communicates strictly with the parent EC2 instance via a local virtual socket (vsock) channel.
    • Cryptographic Attestation: The Nitro Hypervisor generates signed attestation documents proving the enclave's code hash (PCRs) to AWS KMS before releasing decryption keys.
  • Confidential Computing with AMD SEV-SNP: Encrypts VM memory using hardware-generated keys managed by the AMD Secure Processor, shielding memory contents from the host hypervisor.

Google Cloud Confidential Computing Portfolio GCP

  • Confidential VMs:
    • Leverages AMD SEV (Secure Encrypted Virtualization) and SEV-SNP to encrypt all RAM using ephemeral hardware keys generated by the secure processor.
    • Zero code change required: Toggle a single checkbox on Compute Engine or GKE nodes. Memory encryption has negligible performance overhead (< 2–4%).
  • Confidential Space:
    • Zero-trust multi-party data collaboration platform.
    • Allows multiple untrusted parties (e.g., healthcare institutions or banks) to pool sensitive data for model training or aggregation without any party (or Google) seeing the raw data.
    • Uses OpenID Connect (OIDC) cryptographic attestation tokens issued by the Google Cloud Attestation Service to release decryption keys strictly to authorized container workloads.

11. Principal-Level Threat Modeling & Whiteboard Scenarios

Scenario A: Zero-Trust Multi-Party Healthcare Data Collaboration

Threat Model: Two competing pharmaceutical companies wish to run a joint ML cancer-detection model across their proprietary genomic datasets. Neither party can expose their raw genomic data to the other, nor can they trust cloud administrative staff with access to unencrypted data.

  • AWS Architecture:
    • Deploy workloads inside AWS Nitro Enclaves on AMD SEV-SNP compute instances.
    • Both parties upload encrypted datasets to an isolated S3 bucket encrypted with their respective AWS KMS CMKs.
    • The Nitro Enclave boots a mutually audited container image and generates a cryptographic attestation document.
    • Both parties configure KMS Key Policies to release decryption keys strictly if the attestation document matches the expected image measurement hashes (PCR0/PCR1/PCR2).
    • The model trains entirely within isolated enclave memory; results are written back to a shared bucket; raw data is destroyed upon enclave shutdown.
  • Google Cloud Architecture:
    • Deploy workloads using Confidential Space on Google Compute Engine.
    • Both parties store datasets in private Cloud Storage buckets encrypted using Cloud KMS CMEK.
    • The Confidential Space workload boots a certified container in an AMD SEV-SNP encrypted VM environment.
    • The container requests an attestation token from the Google Cloud Attestation Service, validating the boot state and image signature.
    • Cloud KMS evaluates the attestation claims via Workload Identity Federation and releases temporary decryption keys.
    • Neither party, nor Google system administrators, can inspect the physical RAM or intercept unencrypted genomic data.
Scenario B: Ransomware Containment & Incident Response Pipeline

Threat Model: An attacker obtains compromised developer credentials, spins up unauthorized compute for cryptomining, and begins enumerating object storage buckets to exfiltrate and encrypt customer data.

  • AWS Response Workflow:
    • Detection: Amazon GuardDuty triggers findings: CryptoCurrency:EC2/BitcoinTool.B!DNS and Exfiltration:S3/AnomalousBehavior.
    • Ingestion & Triage: Findings stream into AWS Security Hub and Amazon EventBridge.
    • Automated SOAR Action:
      1. An EventBridge rule invokes an AWS Step Functions state machine.
      2. Attaches an emergency IAM Deny Policy (AWSRevokeOlderSessions) to the compromised IAM credentials.
      3. Changes the EC2 Security Group to an isolated quarantine group (no ingress/egress).
      4. Invokes GuardDuty Malware Protection to trigger an automated snapshot of the attached EBS volumes for digital forensics.
      5. Ingests findings into Amazon Detective to visualize lateral movement graphs.
  • Google Cloud Response Workflow:
    • Detection: SCC Event Threat Detection flags Execution: Cryptomining and Exfiltration: Large Outbound Storage Copy; VMTD flags malicious processes in RAM.
    • Ingestion & Correlation: Telemetry streams in real time into Google Security Operations (Chronicle SIEM), correlating historical DNS queries with Mandiant threat intel.
    • Automated SOAR Action:
      1. Chronicle SOAR automatically triggers an incident response playbook.
      2. Disables the compromised Service Account or revokes the OAuth session tokens via Cloud IAM APIs.
      3. Applies a Hierarchical Firewall Rule or quarantine network tag to sever network connectivity to the affected VM.
      4. Dynamically adds the target Cloud Storage bucket to a restricted VPC Service Controls (VPC-SC) perimeter, immediately dropping all unauthorized external API traffic.
