1. Resource Hierarchy & Tenancy Models

The tenancy model defines how authorization policies propagate across accounts, folders, and resources, dictating isolation blast radius and governance delegation.

================================================================================================== RESOURCE HIERARCHY COMPARISON ================================================================================================== AWS ORGANIZATIONS GOOGLE CLOUD RESOURCE MANAGER [ Organizations Root ] [ Organization (Cloud Identity Domain) ] │ │ ┌──────┴──────┐ ┌──────┴──────┐ [ Core OU ] [ Workload OU ] [ Folder: Core ] [ Folder: Workloads ] │ │ │ │ [ Account ] [ Account ] [ Project ] [ Sub-Folder ] │ │ │ │ (IAM Engine) (IAM Engine) (Cloud Storage, [ Project: Prod ] (VPC, S3, (EC2, KMS, BigQuery, GCE) │ Local Roles) Local Roles) (Cloud Storage, GKE) ==================================================================================================

AWS Multi-Account Tenancy AWS

AWS enforces a hard boundary at the Account level. Each AWS account maintains a segregated IAM database and local policy evaluation runtime.

  • AWS Organizations: Management container orchestrating nested Organizational Units (OUs, max depth of 5).
  • Service Control Policies (SCPs): Organization-level guardrails. Crucial rule: SCPs never grant access; they define an authorization filter (allowlist or denylist) that caps the maximum available permissions for member accounts.
  • Resource Control Policies (RCPs): Centrally applied guardrails that constrain incoming access to AWS resources across accounts, preventing public data exfiltration.
  • Cross-Account Isolation: Explicit authorization is mandatory on both sides. Account A must grant permission to assume a role or access a resource, and Account B's identity must explicitly be granted permission to invoke the cross-account action.

Google Cloud Lattice Inheritance GCP

Google Cloud operates a single unified global resource tree rooted at the Organization node (tightly anchored to a Cloud Identity / Google Workspace domain).

  • Folders & Projects: Folders can be nested up to 10 levels deep. Projects act as API enablement, quota, and billing containers—not isolated identity boundaries.
  • Lattice Inheritance Model: IAM bindings applied at higher levels (Org or Folder) propagate downward to all descendent resources additively:
    Effective Permissions = Union(Org, Folder_1, ..., Folder_n, Project, Resource)
  • Non-Revocable Allow: A permission granted at an Organization or Folder node cannot be revoked at a child Project level using Allow policies.
  • Hierarchical Deny Policies: Explicit Deny rules placed at Org or Folder levels that override downstream Allow bindings, evaluated prior to standard IAM checks.

2. Identity Constructs & Principal Specifications

Understanding the distinction between human operators, system agents, and machine identities across both platforms.

Principal Type Amazon Web Services (AWS) Google Cloud Platform (GCP) Key Architectural Difference
Superuser Root User: Account-level email/password + hardware MFA. Cannot be restricted by IAM policies within its account. Cloud Identity Super Admin: Manages domain settings. Has no automatic access to resource data unless assigned explicit IAM roles. AWS Root has inherent, unconditional bypass within its account. GCP Super Admin must explicitly bind permissions to its own identity.
Human User IAM User (legacy static keys/passwords) or IAM Identity Center User (SSO). user:alice@company.com (Cloud Identity, Google Workspace, or federated external SAML/OIDC identity). GCP treats the user email as a first-class global identity. AWS legacy IAM users are scoped strictly to a single AWS account.
Group Entity IAM Group (Collection of IAM users). Cannot be referenced as a Principal in resource policies. group:devs@company.com or Dynamic Groups. Can be directly targeted in IAM policy bindings everywhere. GCP groups can be used in IAM bindings across any resource level. AWS IAM Groups cannot be used in trust or resource-based policies.
Machine Identity IAM Role (No long-term credentials; assumed via STS for temporary sessions). Service Account (Email-based machine identity; can be both an Actor/Identity and a Target Resource). GCP Service Accounts have a dual nature: users can hold permissions on the SA to impersonate it, while the SA holds roles on cloud resources.
System / Managed Agent Service-Linked Role (SLR): Predefined role created automatically by AWS services to manage customer resources. Service Agent: Google-managed service account (e.g., service-{project_number}@compute-system.iam.gserviceaccount.com). Both represent platform automation acting inside customer environments with least-privilege scoping.
The Dual Nature of GCP Service Accounts

In GCP, an identity requires the roles/iam.serviceAccountUser or roles/iam.serviceAccountTokenCreator role granted on a Service Account resource to impersonate it. Once impersonated, the actor assumes the outbound permissions assigned to that Service Account on target projects and resources.

3. Policy Grammars & Authorization Engines

A deep architectural look at how policy documents are structured and evaluated at runtime.

AWS Policy Types & Evaluation Pipeline AWS

AWS parses six discrete policy tiers during every API invocation:

  1. Explicit Deny Check: Scans all attached policies. Any explicit Deny results in immediate request termination.
  2. Service Control Policies (SCPs): Must evaluate to Allow; otherwise, authorization fails.
  3. Resource-Based Policies: S3, KMS, SQS policies. In cross-account calls, a valid resource policy can establish trust.
  4. Identity-Based Policies: Attached to User or Role. In single-account calls, an Allow from either identity or resource policy satisfies access.
  5. Permissions Boundaries: Managed policy setting the ceiling for maximum granted permissions.
  6. Session Policies: Passed dynamically via STS during role assumption to restrict the active session.

GCP IAM Binding Model & CEL Expressions GCP

GCP evaluates access using declarative bindings and Common Expression Language (CEL):

  1. Hierarchical Deny Evaluation: Evaluates Deny policies attached to Org, Folder, or Project. Any matching deny immediately rejects the request.
  2. Hierarchy Traversal (Upward Walk): Checks bindings on the resource itself, then its parent Project, parent Folders, and the Organization node.
  3. CEL Condition Evaluation: Evaluates boolean expressions against attributes such as request.time, resource.matchTag(), or request.auth.claims.
  4. Default Implicit Deny: If no matching Allow binding is found across the tree, access is denied.

4. Token Mechanics & Ephemeral Credentials

Production security mandates eliminating static credentials in favor of short-lived cryptographic tokens.

Primary APIs AssumeRole, AssumeRoleWithWebIdentity, AssumeRoleWithSAML, GetFederationToken generateAccessToken, generateIdToken, signBlob, signJwt
Credential Payload Triad: AccessKeyId (starts with ASIA...), SecretAccessKey, SessionToken OAuth 2.0 Bearer Access Token (opaque or JWT) or OpenID Connect (OIDC) ID Token
Session Duration Configurable: 15 minutes to 12 hours (Role setting); chained assumption limited to 1 hour Default: 1 hour (Extendable to 12 hours via Org Policy constraint: constraints/iam.allowServiceAccountCredentialLifetimeExtension)
Request Signing Protocol AWS SigV4 / SigV4A: HMAC-SHA256 hash computed over canonicalized request string and headers locally on the client. Bearer Authorization: HTTP header Authorization: Bearer ya29... validated against Google Front Ends.
Revocation Capabilities Revoke active sessions by attaching an inline policy with aws:TokenIssueTime condition to the role. Service account keys can be disabled/deleted immediately; active OAuth access tokens expire naturally within their 1-hour window.

5. Workload Identity Federation (Keyless Machine Auth)

Cross-cloud and CI/CD pipelines (GitHub Actions, GitLab, Kubernetes, on-premises machines) can authenticate securely without long-lived service account keys or IAM user credentials.

================================================================================================== OIDC WORKLOAD IDENTITY FEDERATION FLOW (GITHUB ACTIONS / K8S) ================================================================================================== [ External Workload ] ──────── 1. Fetch Signed OIDC Token (JWT) ──────► [ External Identity Provider ] (GitHub / On-Prem / K8s) (Token Issuer / JWKS) │ │ 2. Send OIDC Token (Subject, Audience, Claims) ▼ [ Cloud STS Endpoint ] ◄────── 3. Cryptographically Verify Signature ────┘ (AWS STS / GCP STS) against External Provider JWKS URL │ │ 4. Issue Ephemeral Cloud Credentials ▼ [ Workload Authenticated ] - AWS: ASIA... Credentials (AWS SigV4) - GCP: Short-Lived OAuth 2.0 Access Token ==================================================================================================

AWS Machine Identity Patterns AWS

  • EKS IAM Roles for Service Accounts (IRSA): An OIDC Discovery endpoint is created for the Kubernetes cluster. Pods inject short-lived projected tokens to call sts:AssumeRoleWithWebIdentity.
  • EKS Pod Identity: Modern alternative to IRSA. An in-cluster daemon agent intercepts credential calls, eliminating the need to manage individual OIDC provider URLs in IAM trust policies.
  • AWS IAM Roles Anywhere: Leverages X.509 PKI certificates issued by an on-premises Certificate Authority (CA) to authenticate servers, physical machines, and hybrid workloads against AWS STS.

GCP Workload Identity Federation GCP

  • Workload Identity Pools: Logical containers managing external trust domains (AWS, Azure, GitHub Actions, Okta).
  • Attribute Mappings & Conditions: Maps incoming claims to Google attributes (e.g., google.subject=assertion.sub) and validates conditions using CEL expressions (e.g., assertion.repository == "enterprise/core-repo").
  • GKE Workload Identity: Replaces metadata server endpoints on GKE nodes with a secure metadata proxy. Automatically maps Kubernetes Service Accounts (KSA) to Google Service Accounts (GSA).

6. Workforce Identity Federation & Enterprise SSO

How enterprise employees (humans) authenticate into cloud consoles, CLI sessions, and internal tools using corporate identity providers (Okta, Ping, Microsoft Entra ID).

AWS IAM Identity Center (formerly AWS SSO) AWS

  • Directory Synchronization: Native integration with enterprise IdPs using SAML 2.0 for authentication and SCIM (System for Cross-domain Identity Management) for automatic user/group provisioning.
  • Permission Sets: Centrally defined policy bundles assigned across AWS Organization accounts. When assigned, IAM Identity Center automatically deploys corresponding IAM roles into target accounts.
  • Session Management: Configurable console and CLI session durations with multi-factor authentication (MFA) enforcement at sign-in.
  • Application Assignments: Built-in support for assigning workforce access to AWS-managed applications (Amazon Q, QuickSight) and third-party SAML SaaS tools.

GCP Workforce Identity Federation & Cloud Identity GCP

  • Cloud Identity Engine: Google's built-in Identity-as-a-Service (IDaaS) platform. Syncs users and groups from on-premises directories via Google Cloud Directory Sync (GCDS) or federates via SAML 2.0 / OIDC.
  • Workforce Identity Federation: Enables workforce users (via Okta, Entra ID) to access Google Cloud console and gcloud CLI without creating synced user accounts in Cloud Identity.
  • Attribute-Based Access Control: Pass corporate attributes (department, cost-center) in the IdP assertion to dynamically determine resource access via CEL conditions.

8. Zero-Trust Perimeters & Context-Aware Access

Pure identity credentials can be stolen or compromised. Securing enterprise environments requires binding authorization decisions to network location, device health, and cryptographic boundaries.

AWS VPC Endpoints & Condition Keys AWS

AWS enforces perimeter control through combined IAM condition keys and network endpoint policies:

  • aws:sourceVpc / aws:sourceVpce: IAM condition keys that restrict API execution strictly to calls originating from within designated VPCs or specific VPC Endpoint IDs.
  • aws:PrincipalOrgID: Restricts resource access exclusively to principals belonging to a specific AWS Organization ID, preventing external cross-account access.
  • VPC Endpoint Policies: Resource policies attached to AWS PrivateLink endpoints that restrict which S3 buckets or KMS keys can be reached through the interface, blocking unauthorized exfiltration.

GCP VPC Service Controls (VPC-SC) GCP

GCP decouples identity authorization from network perimeter boundaries via VPC Service Controls:

  • Service Perimeters: Cryptographic boundaries placed around Google-managed PaaS APIs (Cloud Storage, BigQuery, Cloud SQL).
  • Data Exfiltration Prevention: Even if a bad actor steals valid project owner credentials, API requests originating outside the perimeter (or targeting storage buckets outside the boundary) are blocked at the Google API proxy layer with HTTP 403.
  • Access Context Manager: Context-aware rules evaluating client IP subnet, geographic region, device posture (Chrome Enterprise), and user identity before allowing perimeter traversal.

9. Comprehensive IAM Capability Matrix

Direct architectural comparison across core identity and access management functions.

Functional Category Amazon Web Services (AWS) Google Cloud Platform (GCP) Architectural Assessment
Attribute-Based Access Control (ABAC) Native support using resource tags, principal tags, and session tags (aws:PrincipalTag, aws:ResourceTag). Supported using Resource Manager Tags evaluated inside CEL conditions (resource.matchTag()). AWS ABAC is more universally supported across services; GCP CEL provides richer programmatic logic.
Cross-Account / Cross-Project Trust Requires bidirectional configuration (IAM Role Trust Policy + Identity-based AssumeRole permission). Unidirectional binding directly grants external identities or service accounts access to target resources. GCP delegation is simpler to administer; AWS bidirectional model enforces stricter bilateral accountability.
Delegated Administration Permissions Boundaries prevent privilege escalation by limiting what delegated admins can assign. Custom Roles + Hierarchical IAM bindings scoped strictly to specific Folders or Projects. AWS Permissions Boundaries are purpose-built for secure developer self-service role creation.
Deny Policy Mechanics Explicit Deny inside any identity, resource, or session policy takes precedence over all Allow rules. IAM Deny Policies placed at Org/Folder level override any Allow bindings across the tree. Both provide robust guardrails; GCP separates Deny policies into distinct policy objects for clean management.
Machine Key Management Static IAM user access keys (discouraged; require manual rotation or Secrets Manager automation). Service account private keys (JSON). Can be completely disabled enterprise-wide via Organization Policy. GCP allows centralized enforcement to eradicate static machine keys entirely via Org Policy.

10. Principal-Level Whiteboard Scenarios

Scenario A: Hardening Against SSRF Instance Metadata Exfiltration

Threat: A compromised web application allows an attacker to issue requests to the link-local metadata address (169.254.169.254) to exfiltrate temporary credentials.

  • AWS Hardening Protocol:
    1. Enforce IMDSv2 globally using an SCP requiring ec2:MetadataHttpTokens = required.
    2. Configure ec2:MetadataHttpPutResponseHopLimit = 1. This ensures the required PUT session token cannot traverse beyond the host instance to container runtimes or reverse proxies.
    3. Attach IAM Permission Boundaries restricting role credentials to the specific VPC CIDR using the aws:sourceVpc condition.
  • Google Cloud Hardening Protocol:
    1. Deploy workloads on GKE with Workload Identity enabled. This replaces the default link-local metadata server with a secure pod-level proxy that isolates credentials.
    2. Enforce Organization Policy: constraints/compute.disableGuestAttributes and disable legacy metadata endpoints.
    3. Enforce Organization Policy: constraints/iam.disableServiceAccountKeyCreation to ensure zero static keys exist on VMs.

Scenario B: Multi-Tenant Zero-Trust Analytical Pipeline

Requirement: Allow an external analytics team in a partner account/project to process data in an internal object storage bucket without exposing encryption keys or enabling data exfiltration.

  • AWS Whiteboard Implementation:
    1. Configure S3 Bucket Policy to allow s3:GetObject and s3:ListBucket exclusively to the Partner Role ARN.
    2. Encrypt data using an AWS KMS Customer Managed Key (CMK). Explicitly add the Partner Account ID to the KMS Key Policy with permissions for kms:Decrypt (S3 access alone fails without explicit cross-account KMS delegation).
    3. Attach a condition requiring aws:SecureTransport: true and enforce VPC Endpoint access via aws:sourceVpce.
  • Google Cloud Whiteboard Implementation:
    1. Grant roles/storage.objectViewer on the specific Cloud Storage bucket directly to the partner identity (e.g., serviceAccount:etl-worker@partner-project.iam.gserviceaccount.com).
    2. When using Customer-Managed Encryption Keys (CMEK), grant roles/cloudkms.cryptoKeyDecrypter to the internal Cloud Storage Service Agent, not the partner identity. GCP transparently handles the KMS decryption on behalf of authorized bucket readers.
    3. Enforce a VPC Service Controls (VPC-SC) perimeter around the storage bucket with an Ingress Rule that permits API calls only from the partner's verified project network perimeter.
